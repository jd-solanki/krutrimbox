# Inspect a stuck sandbox with a deterministic `kb status`, not an AI agent

When a Factory Run looks stuck, an operator needs to know **what the Sandboxed Agent is doing** — busy, stalled, or gone. krutrimbox answers this with a deterministic `kb status --issue <n>` command that reads the sandbox's live process tree, the Target Issue Lock, the network policy log, and the sandbox's git state, then prints a **Sandbox Verdict** (`BUSY` / `STALLED` / `EXITED`) with the evidence beneath it. It reuses `sbx` reads only — no LLM, no tokens, no agent CLI — so it runs offline while a run is wedged.

This deliberately does **not** wrap a coding agent. An earlier design paired `kb status` with a `kb query "…" --agent <agent>` that would spawn an agent to reason about the sandbox. It was dropped: to observe the *inner* Sandboxed Agent you need an *outer* vantage point, so `kb query` would run a full coding agent on the host with the operator's own credentials and filesystem — a real posture shift for a project that keeps every agent inside a sandbox behind a read-only token. The AI-driven inspection stays what it already is: a copy-paste prompt in the [Inspect a Sandbox with AI](../vitepress/guide/inspect-sandbox-with-ai.md) guide, which the operator runs in whatever agent they choose.

The Sandbox Verdict is intentionally coarser than the AI prompt's. The prompt splits the stalled case into `BLOCKED` (a denied host) versus `WEDGED` (waiting on stdin); `kb status` collapses both into one **`STALLED`** and *attaches* the recent policy-log DENY lines and git state as evidence rather than asserting a cause. Asserting "blocked on `registry.npmjs.org`" requires guessing which host the stuck command wants — the exact fuzzy judgment we removed the AI to avoid — so reproducing it in deterministic code would mean a brittle package-manager→host table that contradicts the command's language-agnostic goal. `kb status` is confident about what it can measure (CPU-time delta across two samples, process presence, DENY lines, diffstat) and silent about what it can only guess.

## Considered Options

- **A single `kb inspect --agent <agent>` flag that flips between deterministic and AI modes.** Rejected. A flag that changes a command's entire nature is a smell: the two modes have different output contracts (parseable stats vs. freeform prose), failure modes (never fails vs. burns tokens / needs an agent CLI), and dependencies. Splitting on the verb is honest; and since `kb query` was then dropped entirely, only `kb status` remains.
- **Reconstruct the sandbox name from the repository slug.** Rejected. `getRepositorySlug()` shells out to `gh repo view` — a network call — which would make an offline inspection command require GitHub auth just to name the sandbox. Instead `kb status` scans `sbx ls` for the slug-independent `krutrimbox-issue-<n>-…-<agent>` shape, so it needs only `sbx` plus local reads.
- **Require `--agent`, mirroring `kb run`.** Rejected as the default. `kb run` *creates* work and must state its backend explicitly (ADR-0016); `kb status` *observes* work whose agent is already baked into the sandbox on disk, so the agent is inferred from `sbx ls` and `--agent` is required only to break the rare two-backends-same-issue tie.
- **Extend `CommandSandboxRunner` with an `inspect()` method.** Rejected. That class drives a sandbox through the run *lifecycle* (create, checkout, commit, push, teardown) — all mutating. Inspection is read-only with a different construction and lifetime, so it lives in a separate `SandboxInspector` that shares only the `CommandRunner` seam.

## Consequences

- A new `kb status` subcommand and a read-only `SandboxInspector`; `FileTargetIssueLockStore` gains a read-only `isHeld(issueNumber)` query so the inspector reads liveness without knowing the lock's directory layout.
- Absence and a stopped-but-present sandbox are **reportable states, not errors** (exit 0); only a genuine `sbx`/usage failure exits non-zero. The host-log tail is shown only in the `STALLED`/`EXITED` cases, where the agent is not mid-tool-call, because a busy run's log tail looks frozen (krutrimbox flushes a log line only when a tool call completes).
- The busy-vs-stalled call rests on the delta of the agent subtree's **cumulative CPU time** between two `ps` samples, not on `%CPU` (which `ps` reports as a lifetime average that barely moves over a two-second window).
